HLD

Arquitectura de solución — topología

La VM solo mueve punteros y delega. Object Storage es data-lake temporal (lifecycle 7 días); ADB 23ai guarda metadatos, la cola de estado y los vectores; los secretos se traen de Vault a tmpfs en runtime vía Instance Principal.

LLD

Flujo de ejecución — dos etapas efímeras aisladas

Cada docker run --rm arranca en baseline: el pico de Chromium (Etapa A) y el de PDF + LLM (Etapa B) nunca se suman. El handoff durable (Object Storage + estado en ADB) hace la Etapa B reanudable. Franja roja = llamadas a Claude.

FSM

Máquina de estados del pliego — idempotente y reanudable

La Etapa B reanuda cualquier estado no-terminal vía la cola SKIP LOCKED. Un crash entre transiciones no pierde ni duplica trabajo (guardas por proceso_id).

Qué cambió frente al PNG original

  • Ollama · Llama 3 8B Q4 residente → eliminado: 8B Q4 ≈ 4.7 GB de pesos, imposible sobre 1 GB. Razonamiento 100% en la API de Claude.
  • ChromaDB / Qdrant residente → eliminado: redundante y viola el reposo efímero. Vector store único = ADB 23ai.
  • Embeddings vía Cohere / OpenAI → in-database (ONNX en ADB): cero costo, cero RAM en la VM, mono-vendor.
  • Pipeline monolítico → dos etapas efímeras aisladas (scrape → analyze) para que los picos de memoria nunca coexistan.
  • Se añadieron cola durable (SKIP LOCKED), máquina de estados, retry policies y guardia de cuota de tokens.
